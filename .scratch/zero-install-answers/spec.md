# Spec：讓零安裝場景給出正確且完整的答案

**Tracker**: local markdown
**Labels**: `ready-for-agent`
**Status**: ready
**Created**: 2026-07-30

---

## Problem Statement

使用者用兩種方式接觸這個服務，兩條路都給不出可用的答案。

**從 Google 搜尋進來的人拿不到答案。** 搜「臺北到花蓮 火車時刻表」點進落地頁，頁面上只有「最快約 2 小時 8 分、每日約 43 班、首班 00:20 末班 22:01」這種摘要 —— 沒有任何一個車次號碼、除首末班外沒有任何一個時刻。要看到真正的班次，得等 SPA 載入約 455 kB JavaScript，再抓約 0.55 MB 的當日班表。使用者的實際行為是跳回 Google 換一個結果。

**已經進到 SPA 的人拿到錯的票價。** TRA ODFare 資料集對每一組 OD 都同時提供順行與逆行兩筆（環島兩個方向），票價 getter 只依目的地站篩選、不區分方向，上層再以車種為鍵做覆蓋，結果一律取到檔案中較後的逆行那筆。臺北→花蓮自強系顯示 NT$1676，正確的北迴票價是 NT$583。抽樣 30 個起站檔、7170 組 OD，其中 7164 組（100%）都有雙方向；最壞的案例（相鄰站之間）誤差達 73 倍 —— 正確 NT$29，可能顯示 NT$2108。

這兩件事合起來破壞的是同一個東西：這個服務相對於原生時刻表 App 的唯一結構優勢，是「零安裝、點連結就用、Google 找得到」。落地頁不給答案等於放棄這個優勢；票價錯誤等於把僅存的信任也一起燒掉 —— 缺功能的使用者只是覺得不好用，看到錯票價的使用者會相信它、據此決定行程、並轉述給別人。

## Solution

**一、票價方向消歧義。** 在 API 層與資料刷新流程之間新增一個共用的純函式契約：給定同一 OD 的多筆 ODFare 紀錄，同一車種只保留行駛距離最短的那一筆（即實際直達路線）。票價 getter 在回傳前套用它，涵蓋靜態檔與 live 降級兩條路徑；資料刷新腳本在按起站切檔時套用它，讓 committed 資料集與使用者每次搜尋要下載的檔案同時砍半（目錄 517 MB → 約 259 MB，單檔 2.6 MB → 1.3 MB）。

**二、落地頁直接印出班次表。** 靜態落地頁改為列出該 OD 的全部直達班次，依 `ServiceDay` 分成平日與假日兩張表，每列含車次號碼、車種、出發、抵達、行駛時間。尾段時段用瀏覽器原生的可折疊區塊收起，維持頁面零 JavaScript。同時修正目前把整週服務模式當成「每日班次數」的統計。

**三、把不確定性標示出來，而不是假裝沒有。** 落地頁標明資料截止日期，並明確把「今日誤點／停駛」導向 SPA。靜態頁不新增任何 runtime fetch —— 即時性這條軸線本來就贏不了每 10 秒更新的競品，用零 JavaScript 的護城河去換一場必敗的仗不划算。

結果是一句可以對外承諾的定位：**今天以前不會變的事，落地頁在 0.5 秒內全部給你；今天才知道的事，點一下進 SPA。**

## User Stories

1. As a 從 Google 搜尋進來的使用者, I want 落地頁直接列出當天所有直達班次的車次與時刻, so that 我不必等 SPA 載入就能知道幾點有車
2. As a 手機上用行動網路的使用者, I want 落地頁不需要下載 JavaScript 就能顯示班次, so that 我在訊號差的地方也能在幾百毫秒內看到答案
3. As a 通勤族, I want 平日與假日的班次分開列出, so that 我不會把只在週末加開的班次誤認為每天都有
4. As a 週末出遊的使用者, I want 假日班表包含週末加開班次, so that 我規劃週末行程時看到的是實際會開的車
5. As a 想找特定時段的使用者, I want 班次表按時間排序並可展開完整清單, so that 我能直接找到「早上八點多那班」而不是只看到首末班
6. As a 使用高鐵頁面的使用者, I want 101 班的長清單不要一次全部展開, so that 我在手機上不必滑過一整面牆才找到我要的時段
7. As a 只想快速確認末班車的使用者, I want 首班與末班仍然醒目地標示, so that 我不必展開完整表格
8. As a 查詢台鐵票價的使用者, I want 顯示的票價是實際直達路線的票價, so that 我不會看到繞行環島另一側的價格
9. As a 查臺北到花蓮的使用者, I want 自強系票價顯示 NT$583 而非 NT$1676, so that 我不會誤以為這段票價將近兩千元而放棄搭車
10. As a 查相鄰兩站的使用者, I want 短程票價不會顯示成環島一圈的價格, so that 我不會遇到 73 倍的誤差
11. As a 比較車種的使用者, I want 自強、莒光、區間車各自顯示自己的票價, so that 我能判斷用時間換金錢是否值得
12. As a 在靜態資料檔缺失時仍在使用服務的使用者, I want live 降級路徑取得的票價同樣經過方向消歧義, so that 我不會因為看不見的降級而拿到錯的價格
13. As a 每次搜尋都要下載票價檔的使用者, I want 票價檔案體積減半, so that 台鐵搜尋的首次載入更快
14. As a 對資料新鮮度敏感的使用者, I want 落地頁標明資料截止日期, so that 我知道自己看的是哪一天的班表
15. As a 需要知道今天實際狀況的使用者, I want 落地頁明確指引我到即時查詢, so that 我不會誤以為靜態頁上的班表已經反映今天的誤點與停駛
16. As a 外國旅客, I want 英文落地頁同樣包含完整班次表, so that 我不需要看得懂中文也能自行查到班次
17. As a 用 Google 搜尋的使用者, I want 搜尋結果的摘要與頁面實際內容一致, so that 我不會點進去發現承諾的東西不在頁面上
18. As a 搜尋引擎爬蟲, I want 班次資料以純 HTML 呈現且結構化標記與可見內容一致, so that 我能正確索引並在答案型結果中引用
19. As a 維護者, I want 票價消歧義的規則寫在單一個被所有消費端共用的純模組裡, so that 未來新增的消費端自動受保護、不必在每個地方重複實作
20. As a 維護者, I want 票價消歧義有以真實資料集為 fixture 的測試, so that 資料刷新後若 TDX 改變回傳結構我能立刻知道
21. As a 維護者, I want 落地頁上聲明的班次數與實際印出的列數由自動化檢查保證一致, so that 統計數字不會再度與內容脫節
22. As a 維護者, I want 自動化檢查守住「落地頁零 JavaScript」, so that 未來的修改不會在無意間拆掉這個效能護城河
23. As a 維護者, I want 落地頁使用 committed 的每週通用時刻表而非 14 天每日快照, so that 頁面不會在兩天的資料刷新週期之間掛著過期的具名班次
24. As a 專案負責人, I want 台鐵票價在人工核對絕對值之前仍不上 SEO 頁, so that 我不會把還沒驗證的價格公開索引出去

## Implementation Decisions

### ODFare 方向消歧義

- 新增一個**純函式模組**承載規則：輸入同一起站的 ODFare 紀錄集合，對每一組（目的地站, 車種）只保留 `TravelDistance` 最小的紀錄。最短距離即實際直達路線；環島反向那筆一律丟棄。
- 該模組是**共用契約**，同時被瀏覽器端與 build 期腳本 import，因此**不得使用任何 Node 或 DOM global**。這與現有的 affiliate 契約模組、以及每日時刻表編解碼模組是同一個既定模式。
- **TRA 票價 getter 在回傳前套用消歧義，兩條路徑都套** —— 靜態檔路徑與 live TDX 降級路徑。降級路徑同樣會拿到未消歧義的原始資料，只修其中一條會讓 bug 在最不易察覺的路徑上存活。
- **資料刷新腳本在按起站切檔時套用同一個模組**。這是效能修正而非正確性修正：committed 目錄約 517 MB → 約 259 MB，單一起站檔 2.6 MB → 1.3 MB（該檔是使用者每做一次台鐵搜尋就要下載的東西）。筆數為精確的 50%。
- **SPA 的班次卡票價對照邏輯不修改。** 它以車種為鍵、後者覆蓋前者；一旦 getter 保證每個車種只回一筆，覆蓋就無害。消歧義收在 getter 內部是為了讓上層與未來的消費端都不需要知道這件事存在。
- 正確性修正可獨立於資料刷新上線並立即生效；體積修正隨下一次排程刷新（或手動執行刷新）進來。兩者互不阻塞。
- THSR 票價不受影響 —— 高鐵 ODFare 沒有環島方向歧義，且落地頁已在使用它。

### 落地頁班次表

- 資料來源維持 committed 的**每週通用時刻表**，不使用 14 天每日快照。理由：資料刷新週期為每兩天，若印出具名日期的班次，頁面會長期掛著過期時刻；而在交通資訊頁面上顯示過期時刻是信任問題，與現行「不把不可靠資料放上索引頁」的立場一致。
- 依 `ServiceDay` 分為**平日**與**假日**兩張表。每天都行駛的班次會同時出現在兩張表中。
- **列出全部直達班次**，不做取樣。每列包含車次號碼、車種、出發時刻、抵達時刻、行駛時間。取樣等於沒有回答問題，使用者仍得跳 SPA。
- 尾段以**瀏覽器原生的可折疊區塊**收起，切點依**時段**（例如中午之後）而非固定列數 —— 各 OD 班次密度差距達四倍（26 班 至 101 班），固定列數在稀疏路線上會產生怪異的切點。折疊區塊內的內容仍是可爬取的 HTML。
- **落地頁維持零 JavaScript。** 不新增 runtime fetch。頁面現有的三段結構化標記是資料而非可執行程式，維持現狀。
- **修正班次數統計**：現行的掃描邏輯完全不讀 `ServiceDay`，把整週服務模式中所有服務該 OD 的班次都計入「每日班次」，因此目前的數字偏高。改為分別計算平日與假日班次數，文案同步改寫。
- 掃描邏輯在同一個迴圈中本來就已取得每一班的出發、抵達與車種，只是計算完聚合統計後丟棄。班次表所需資料無須新增任何資料來源。
- 中英文兩套落地頁皆需包含班次表。

### 不確定性標示

- 落地頁標明**資料截止日期**（來自產生時所使用的資料集）。
- 「今日誤點／停駛」明確導向 SPA；落地頁不承擔即時性。
- 台鐵票價**維持不上 SEO 頁**，直到絕對值經人工與台鐵官方管道核對。方向消歧義是必要條件而非充分條件。

## Testing Decisions

好的測試只驗**外部可觀察的行為**，不驗實作細節。這裡的外部行為有兩種：共用契約模組給定輸入回傳什麼，以及產生出來的落地頁 HTML 長什麼樣。兩者都不需要知道內部是怎麼算的。

Seam 數量刻意壓在 **2 個，其中 1 個是既有的**。

### Seam 1（新增）— 方向消歧義契約模組

- 以 Node 內建測試 runner 透過 tsx 執行，形式與現有十餘個測試檔一致，並新增對應的 npm script。
- **以真實資料集為 fixture**，而非手寫假資料：直接對 committed 的臺北起站票價檔斷言。這樣測試同時具備迴歸保護與「TDX 回傳結構改變時立刻失敗」的偵測能力。
- **斷言必須是關係式的，不得寫死票價金額或距離。** 期望值由 fixture 當場導出：「回傳的那筆，其行駛距離等於該（目的地站, 車種）所有候選中的最小值」、「回傳的不是距離最大的那筆」。票價會隨每兩天的資料刷新與台鐵調價變動，寫死金額會在**合法調價後產生假警報**，並把一個尚未與台鐵官方管道核對的數值（583）固化成規格。本文件各處出現的金額與體積數字皆為 2026-07-30 的觀測值，供人工核對規模之用，不是斷言常數。
- 涵蓋案例：雙方向 OD 取到短距離那筆；單方向 OD 不受影響（抽樣中有 6 組）；同 OD 多車種各自獨立消歧義；缺少距離欄位時的行為。
- 先寫失敗的測試（斷言 583），確認它在修正前確實失敗，再修。
- **Prior art**：每日時刻表格式的 round-trip 測試（以編解碼對稱性釘住格式）、TDX 資料完整性測試（直接對真實資料檔斷言）、affiliate 契約測試（純模組 + 契約漂移防護）。

### Seam 2（擴充既有）— SEO 產物驗證

擴充既有的 SEO 驗證腳本。它已經是「產生出來的落地頁正確嗎」的唯一守門員，已在逐頁 walk 中英文兩套落地頁做斷言，且讀取 committed 產物、不需要 build。

新增的斷言全部從**輸出面**驗證，不重算資料：

- 每頁存在平日與假日兩張班次表，且可辨識
- 每一列都含車次號碼與出發、抵達時刻
- **各表列數與頁面文案聲明的該類別班次數一致** —— 這條自我一致性斷言會自動抓到現行統計與內容脫節的問題，且不需要把 `ServiceDay` 分組計算複製到測試裡
- 可折疊區塊存在，且折疊的是時段尾段
- 頁面不含外部 script 引用（守住零 JavaScript）
- 結構化標記中的班次數與可見內容一致

### 刻意不測的東西

- **`ServiceDay` 分組邏輯不抽出來單獨測。** Seam 2 的「列數 == 聲明數」已經覆蓋它；抽成獨立模組只是多一個 seam，換不到額外保障。
- **SPA 的班次卡票價對照邏輯不測**，因為不修改它。正確性由 getter 保證。
- 資料刷新腳本的切檔行為不新增測試 —— 它套用的是 Seam 1 已經測過的同一個模組，且既有的資料完整性測試已涵蓋原子替換行為。

## Out of Scope

- **解禁台鐵票價上 SEO 落地頁。** 前置條件是拿數組 OD 與台鐵官方管道人工核對絕對值，這件事無法由程式完成。目前資料修正後臺北→花蓮自強系為 NT$583，而常見引用值為 NT$440，差距原因未確認。
- **擴充落地頁的 OD 組數（廣度）。** 現有 17 頁。刻意排在深度之後：若每頁都不回答問題，擴到數百頁只會把跳出率放大數百倍。時機取決於 Search Console 數據。
- **追平原生 App 能力**：離線時刻表資料庫、背景推播、桌面小工具、Apple Watch、帳號同步、餘票查詢。這些差距源自「這是網頁」這個載體，補齊等同於出 App。現行的到站提醒僅在分頁開啟時有效，正式站也不具備 socket 推送，本 spec 不改變這個現狀。
- **即時誤點的資料新鮮度追平競品。** 靜態頁贏不了每 10 秒更新的即時追蹤網站；分層而非競爭。
- **訂票 deeplink 的修正。** 另一條獨立工作，其變更目前仍在工作區未提交，且卡在 TDX 模組授權狀態的驗證。
- **THSR 票價邏輯**。無方向歧義，不在本次範圍。

## Further Notes

- 專案文件目前把台鐵票價不上 SEO 頁的原因記載為「資料集的距離與價格不可靠」。這個診斷是錯的：TDX 的資料正確、按車種分價正確、提供環島兩個方向也正確 —— 問題出在**消費端沒有消歧義**。修正後應同步更新該說明，否則會誤導未來的維護者，讓他們以為問題在上游而無從下手。
- 同一份被判定為「不可靠到不能公開索引」的票價資料，一直照樣顯示在 SPA 的班次卡上給使用者。這個矛盾是本 spec 的起點；修正後兩邊的標準應趨於一致。
- 落地頁的英文版與中文版由同一個產生流程輸出，班次表的實作必須一次覆蓋兩者，避免只有中文頁有答案。
- 現行落地頁對「誤點是否即時」的問答已經是誠實的分層說法（明確寫需點擊後才即時讀取）。這個分層是對的，班次表加入後應維持同樣的措辭紀律：靜態頁只承諾固定班表。
